## Decisions made in this plan

### Realisation factor (user's choice: "Realisation factor")

- `puzzle/config.json` gains `"realisation": {"preflop": {"ip": 1.0, "oop": 0.80}, "flop": {"ip": 1.0, "oop": 0.88}, "turn": {"ip": 1.0, "oop": 0.94}}`. The river has no entry (always 1.0). `PuzzleConfig.realisation: Mapping[Street, tuple[float, float]]` as `(ip, oop)`.
- `solve.realisation(street: Street, in_position: bool, all_in: bool) -> float`: 1.0 on the river or when `all_in`, else the config value. **In position** = Hero is the button (heads-up, the button acts last after the flop; pre-flop the decision is about the rest of the hand, so BB is out of position).
- **All-in:** the pot the equity applies to has no betting left: after the action and Villain's reply, a player has no chips behind (`HandState` stacks after the call). Then `r = 1`.
- **Where `r` applies** (the decision street's `r`): Call: `r·e·(P + put) − put`. Pre-river check: `r·e·P`. Bet/raise, Villain-calls branch: `r·e·(P + put + vcall) − put`. Villain-raises branch when Hero calls: `r·e·final − (put + c)` (and Hero's call-or-fold choice uses that value). Fold branches and river values are unchanged.
- `OptionEV.realisation: float = 1.0` (the factor used in a call or check value; 1.0 for bet, raise and fold options, whose factors live on their branches) and `Branch.realisation: float = 1.0` (per branch). New fields go **last** in the dataclasses (constructors are positional). `_option_ev_from_dict` / branch decoding default a missing key to 1.0; encoding always writes it.
- **Simplification codes:** the old code `"realisation"` and its text stay unchanged (pre-M9 puzzles store that code and `api/text.py` `simplification_text` reads the live table, so changing the text would mislabel old results). M9 puzzles use a new code `"realisation_position"` with the text `"Before the river, Hero is assumed to realise a share of equity set by position: in position 100%; out of position 80% pre-flop, 88% on the flop, 94% on the turn. All-in pots realise 100%."`, built from the config (not hard-coded numbers). Update the code-set assertions in `tests/puzzle/test_model.py` and `tests/api/test_text.py`.
- **Custom sizes on old puzzles:** `views.villain_model_current` (views.py ~201) also requires `load_config().version == p.spot.config_version`, so a custom size on a pre-M9 puzzle is refused (409) instead of being graded with a different realisation than its stored options.
- API: the option schema gains `realisation: float` and the branch schema gains `realisation: float`. OpenAPI snapshot and `frontend/openapi.json` / `schema.d.ts` regenerated.
- UI: when `r ≠ 1`, the Maths lines read `EV = r × e × (pot + call) − call` / `= 0.80 × 35.0% × (…) − …` (call), `EV = r × e × pot` (pre-river check), and a line `Realisation (out of position, <street>): 80%` precedes them. "Out of position" is derived from `r < 1` (only OOP factors are below 1), so no new position field is needed. Branch terms use `r × e`. The pot-odds lines (`potOddsLines` in `lib/maths.ts`, shown on the call **and** fold options) compare **realised equity** `r × e`, with `r` taken from the call option, and say so: "Your realised equity (80% of 35.0% = 28.0%) is below the 33.3% pot odds". In the Why text, `facts.py`'s `beats = equity >= pot_odds` uses the call option's `r`, and the pot-odds sentence follows the same rule; the factor and realised equity are in `Facts` so the guardrail allows them.
- `ahead_now`, whole-range equity, the equity guess score and the stats are unchanged (equity is still equity).

### Competence report

New checks in `CHECK_NAMES` (after the existing ten, in this order), bands from the profile's `defence_ratio` unless stated:

MDF convention as in `competence.py` (`prior / (prior + call)`, prior = pot before the bet faced): BB vs a 2.5× open (to 5 chips, BB has 2 in): call 3, prior 7 → MDF 4/7 = 0.571. BTN vs a 3× 3-bet to 15: call 10, prior 20 → 0.50 (vs a 3-bet to 12: 10/17 = 0.588).

| Check | Value | Band |
|---|---|---|
| `defence_overbet` | Villain continue (call + raise) / MDF facing a Hero probe of **2.5× pot** (clamped to all-in by `bet_to`), every street, mean over probes (each probe weight 1, all counted). The 2.5× probe records **only** this check (it does not feed `nuts_fold_max`, `strong_fold_max` or `air_call_max`; call `_facing_records` without them or add a flag). | profile `defence_ratio` |
| `raise_dominated` | River only, at Hero's 33%/75% probes: Villain's raise share `villain * dist[raise]`; Hero's range is the range that made the probe bet (`hero * hero_dist[bet]`) times the Hero profile's call+raise response to the raise; numerator = raising weight with category ≥ MEDIUM and equity vs that range < 0.4, denominator = all raising weight (value + bluff raises); each probe weighted by Hero's bet frequency there, like the defence probes. If fewer than `MIN_SAMPLES` probes have a raise, the check reports as info (not pass/fail) — say so in the report. | `(0.0, 0.10)` |
| `preflop_defence_3bet` | BTN continue (call + jam) vs a 3× 3-bet, weighted by BTN's open range, divided by MDF 0.50 | fixed `(0.90, 1.40)` for every profile (ruling during Task 4: BTN is in position against a 3-bet and realises more than its equity share, so continuing above MDF is correct; the post-flop `defence_ratio` bands don't apply). |

**Info only (in `INFO_NAMES`, printed, never pass/fail):** `preflop_defence_open` = BB continue (call + 3-bet) over the uniform 1,326 combos / MDF 0.571. Today it is 1.39 / 1.47 / 1.02 / 1.55 (TAG / LAG / Tight / Sticky), and that is correct: heads-up the BB closes the action with a price (3 to win 10 needs 30% equity), so defending well above MDF is right, and shrinking it would make Hero's BTN steals grade too well. ### Explanation check (M8 open item: manual check)

- `analysis/explain_check.py`, entry point `explain-check`: `--url http://127.0.0.1:8000 --n 12`. It talks to a **running** app over stdlib `urllib` (no proxy, as `ollama._opener`): for `i` in `range(n)` it creates a puzzle on street `("preflop","flop","turn","river")[i % 4]`, submits an answer (the puzzle view hides EVs, so the option index cycles over first, last, middle: `(0, len-1, len//2)[ (i // 4) % 3 ]`; equity guess 0.5; intent `value` for bets and raises), fetches `/api/attempts/{id}/explanation` (client timeout 300 s), and tallies `source` and `fallback`. It prints a table (street, verdict, source, fallback, seconds) and totals. Exit code 0 always (it measures, it doesn't gate).
- The controller runs it on this machine with a real model against an app on a scratch DB, with `PPT_LLM_TIMEOUT=120` or more (the server-side timeout, default 60 s, otherwise turns slow answers into `timeout` fallbacks), and pastes the output into the sign-off report.

### Guardrail and probe (M8 open items)

- `ollama.probe` first calls `GET /api/version`. `parse_version` takes a leading `major.minor[.patch]` and ignores any suffix. `"0.0.0"` (development builds) is treated as unknown. A parsed, non-zero version below 0.5 → `("unavailable", "Ollama {v} is too old: version 0.5 or newer is needed.")`. Connection refused or timeout on `/api/version` → return the "isn't answering" result at once (don't also try `/api/tags`, which would double the 1.5 s wait). An HTTP error, non-JSON or missing version → continue to `/api/tags` as today. Update `test_ollama.py`'s assertion that the first request is `/api/tags`.
- `guardrail.check_claims` adds an order rule: when `facts.loss_case != "top"`, the first play name (label or gerund form, as `_names` matches them) that appears in the headline must be the top play. It shares the `"headline"` key: if names are missing, that message wins (`"missing …"`); otherwise an order failure gives `"top play not named first"`.
