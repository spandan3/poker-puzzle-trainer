# M5 Table UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A polished, dark, keyboard-driven table screen. The user sees a puzzle exactly as the M4 API serves it (cards, board, history by street, pot, stacks, pot odds, Villain's profile), enters an equity estimate, an optional range read, an action, a size and an intent, submits, and moves to the next puzzle. The full results view is M6; M5 ends each puzzle with a compact result strip.

**Architecture:**
- `frontend/` is a Vite + React + TypeScript app (spec §3), built to `frontend/dist`, which FastAPI already serves (M4, `PPT_FRONTEND_DIST`).
- `src/api/`: `schema.d.ts` (generated from the backend's OpenAPI by `openapi-typescript`), `types.ts` (friendly aliases), `client.ts` (typed `fetch` wrapper with an `ApiError`).
- `src/lib/`: pure logic with unit tests — `format.ts` (chips → bb, percentages), `cards.ts` (parse `"Ah"`), `answer.ts` (actions and sizes derived from the stored options, the custom-size bounds, request building), `history.ts` (group the action log by street, render entry text in bb), `shortcuts.ts` (key map).
- `src/components/`: `Card`, `Table` (oval felt, seat slots), `Seat`, `TableCentre` (board, pot, pot odds), `HistoryPanel`, `AnswerPanel`, `ResultStrip`, `TopBar` (new-puzzle controls, toggles).
- `src/app/`: `usePuzzleFlow` (a `useReducer` state machine over the API) and `App`.
- `src/styles/`: `tokens.css` (CSS custom properties for colours, spacing, radii, shadows, motion) and `global.css`. Components use CSS Modules.
- `src/dev/`: a fixture gallery (`/?gallery`) rendering each component from committed fixtures, used for screenshot reviews.

**Tech stack:** Node 22 LTS, npm with `package-lock.json`, Vite, React 19, TypeScript (strict), ESLint (flat config, `typescript-eslint`, `eslint-plugin-react-hooks`), Prettier, Vitest + Testing Library + jsdom, `openapi-typescript` (dev only), Playwright (dev only, one end-to-end smoke test). No UI kit, no CSS framework, no state library, no data-fetching library, no animation library: the surface is small and polish comes from our own tokens and CSS.

**Spec:** `docs/superpowers/specs/2026-11-10-poker-puzzle-trainer-design.md` (§3 stack and hygiene, §4 the puzzle experience, §11 UI). Roadmap: `docs/superpowers/plans/2026-11-10-roadmap.md` (M5). M4 hand-over: "Open items for M5, M6 and M7" in `docs/superpowers/plans/2026-11-11-m4-api-and-storage.md`.

## Global Constraints

- **The UI never builds an `Action`.** It sends `option` (an index from `PuzzleView.options`) or `custom_to` (chips), as M4 requires. Legal actions, sizes and labels come only from `options`; the UI never decides legality itself. Custom sizes appear only when `custom.allowed`, bounded by `min_to` / `max_to`.
- **Nothing hidden is shown or fetched before a submit.** Before an answer the UI only calls `GET /api/puzzles/current`, `POST /api/puzzles`, `GET /api/puzzles/{id}`, settings and health. Villain's cards are face down until the submit response arrives.
- **Display in big blinds.** Every chip amount shown to the user is `chips / 2`, formatted by one function `formatBb` (`2.5 bb`, `100 bb`, never `2.50`). The API stays in chips. Custom sizes are typed in bb in steps of 0.5 and sent as `custom_to = round(bb * 2)`.
- **Pot odds only from the API.** Show `pot_odds` when it is not null and the setting is on. Never compute pot odds from `to_call` (M4 open item: BTN first in has `to_call` 1 and no call option).
- **No range read on the river.** When `range_read_asked` is false the field is not rendered and `range_read_guess` is not sent.
- **Types come from the API contract.** `src/api/schema.d.ts` is generated from `frontend/openapi.json`, which is generated from `create_app().openapi()`. A backend test fails when `openapi.json` is stale; frontend CI fails when `schema.d.ts` is stale. No hand-written response types.
- **Cross-platform:** every dev command is an npm script or a Node script (`scripts/*.mjs`); no bash or PowerShell. Paths in scripts use `node:path`. Works on Windows and macOS (CI). Line endings follow `.gitattributes`.
- **Dependencies:** pinned through `package-lock.json` (`npm ci` in CI). Every version must have been published at least two weeks ago. TypeScript must be a version `typescript-eslint` supports. No dependency with native binaries except the ones Vite and Playwright bring.
- **Accessibility and motion:** every interactive control is a real `<button>`, `<input>` or `<select>` with a visible focus ring and an accessible name. Cards have `aria-label`s ("Ace of hearts", "face-down card"). Every animation is disabled under `prefers-reduced-motion: reduce`.
- **Original art only.** Cards, chips and the table are drawn with our own SVG and CSS. No copied card images, fonts or icon sets beyond the system font stack and Unicode suit glyphs.
- **Layout ready for five seats:** seats are placed by a slot table around the oval (`bottom`, `bottom-left`, `top-left`, `top`, `top-right`, `bottom-right`). Heads-up uses `bottom` (Hero) and `top` (Villain). No code assumes exactly two seats except the slot assignment.
- **Desktop first:** designed for 1280×800 and up; usable down to 1024 wide; below 900 the side panel stacks under the table. No horizontal page scroll at 1024.
- **Backend changes are minimal and additive** (Task 1 only): `pot_before` on history entries, a `dev_fixtures` module, an `openapi` dump script and its freshness test.
- Commands run from `frontend/` unless stated. Never commit `node_modules/` or `dist/` (already ignored).

## Decisions made in this plan

- **History text is rendered by the UI, in bb.** The API's `text` is in chips ("opens to 5"). Task 1 adds `pot_before: int` (the total pot in chips before the action) to each history entry, so the UI can render the same facts in bb: `opens to 2.5 bb`, `3-bets to 6 bb`, `bets 4 bb (80% pot)`, `raises to 12 bb`, `calls 4 bb`, `checks`, `folds`, `all-in 97.5 bb`. Rules in `lib/history.ts`:
  - The percentage is `to / pot_before` for a bet; raises show no percentage.
  - "all-in" when the action puts the actor's whole stack in: the UI knows this when `to` equals the actor's stack at that point; to avoid replaying, Task 1 also adds `all_in: bool` to history entries.
  - Pre-flop raise names: the first raise is "opens", the second "3-bets", the third "4-bets" (counting raises on the street).
  - `calls` shows the amount added (`to − actor's previous bet on the street`); Task 1 adds `amount: int` (chips added by this action) to make that exact.
  The server `text` stays for M8's narrative.
- **Flow on load:** `GET /api/puzzles/current`; on 404, `POST /api/puzzles` with the chosen street/profile. "New puzzle" (`N`) always POSTs (skipping the current one, by M4's design). After a submit, `N` / "Next puzzle" POSTs.
- **New-puzzle controls** in the top bar: street (`any`, pre-flop, flop, turn, river) and Villain (`settings`, `random`, TAG, LAG, Tight, Sticky — the list comes from `GET /api/settings` `profiles`). These are per-request choices kept in `localStorage` (wrapped in try/catch); they don't change the stored settings profile.
- **Toggles** in the top bar: "Pot odds" and "Show Villain profile", read from and written to `GET`/`PATCH /api/settings` (`show_pot_odds`, `show_profile`). The profile is always shown again in the result strip (spec §11).
- **Answer panel** (Task 4):
  - **Equity:** a slider 0–100 plus a number input, linked, integer percent; required; starts unset ("—") so the user must choose; submit is disabled until set.
  - **Range read** ("% of Villain's range I'm ahead of now"): optional, the same control with a "skip" state (default skipped); hidden on the river.
  - **Action buttons:** one per distinct kind present in `options`, in the order fold, check, call, bet, raise. Bet and raise are one "aggressive" group whose sizes are the options of that kind: shortcut buttons with the option label and the amount in bb (`33% · 2 bb`, `2.5x · 6 bb`, `all-in · 97.5 bb`). The all-in option is labelled all-in even when its kind is bet or raise.
  - **Custom size:** when `custom.allowed`, a bb number input (step 0.5) with the bounds shown; out-of-bounds or non-multiple-of-0.5 input shows an inline error and disables submit. A custom size equal to a listed option's `to` is allowed (the server grades it as that option).
  - **Intent** (value / bluff / semi-bluff): shown only when the chosen action is a bet or raise; optional; cleared when the action changes to a passive one.
  - **Submit:** one request; the button shows a busy state and ignores repeats until the response. 409 (stale model or concurrent submit) and 422 show the server's `detail` inline and keep the answer for editing.
- **Keyboard shortcuts** (disabled while focus is in a text or number input, except `Enter` and `Escape`; never with Ctrl/Alt/Meta):
  - `F` fold, `X` check, `C` call (each only if present), `B` or `R` select the aggressive group.
  - `1`–`9` pick the n-th size shortcut of the aggressive group; `0` focuses the custom size.
  - `V` value, `L` bluff, `S` semi-bluff (only when intent is shown).
  - `E` focuses the equity input, `A` the range-read input.
  - `Enter` submits when valid. `Escape` blurs the focused input.
  - `N` new puzzle / next puzzle. `?` toggles a shortcuts overlay.
  - Shortcut hints are shown on the buttons (small key caps).
- **Result strip (M5's end of a puzzle):** after a submit, the answer panel is replaced by a strip showing the verdict (colour-coded: best / fine / mistake / blunder), EV lost in bb, chosen vs best option, equity guess vs true equity, the revealed Villain profile, and "Next puzzle (N)". Villain's cards flip face up and the remaining board cards are dealt from `reveal.runout`. The full results view replaces this strip in M6.
- **Animations (CSS only):** cards deal from the dealer position with a short stagger on puzzle load (≤ 600 ms total); board cards slide in; Villain's cards flip on reveal; chips/pot fade-update. Durations live in `tokens.css`. All disabled under reduced motion. Animations never block input for more than the deal duration.
- **Errors:** a top-level error banner for network failure or 5xx with a "Retry" button; 503 from generation shows "Couldn't generate a puzzle — try again".
- **Fixtures:** Task 1 adds `poker_trainer.api.dev_fixtures` (dev-only module) which writes, from fixed seeds through the real app with a temp SQLite DB: puzzle views for each street (including pre-flop BTN first in, pre-flop facing a raise, a river, and one with `custom.allowed`), one attempt result for a bet and one for a fold, and the settings view, to `frontend/src/test/fixtures/*.json`. Tests and the gallery use them.
- **OpenAPI snapshot:** `[project.scripts] openapi = "poker_trainer.api.app:dump_openapi"` writes `json.dumps(create_app(AppSettings(_env_file=None)).openapi(), indent=2, sort_keys=True) + "\n"` to a path argument. Backend test `test_openapi_snapshot_fresh` compares it with `frontend/openapi.json`. Frontend `npm run gen:api` runs `openapi-typescript openapi.json -o src/api/schema.d.ts`; `npm run check:api` regenerates to a temp file and fails if it differs.
- **CI:** a `frontend` job on `windows-latest` and `macos-latest`: `setup-node` 22 with npm cache, `npm ci`, `npm run lint`, `npm run typecheck`, `npm run check:api`, `npm test`, `npm run build`. An `e2e` job on `ubuntu-latest`: `uv sync --locked`, `npm ci`, `npm run build`, `npx playwright install --with-deps chromium`, `npm run e2e` (starts the backend with the built frontend on a temp DB and a fixed port, then runs one smoke test).
- **e2e smoke test:** load `/`, see Hero's two cards and Villain's two face-down cards, choose an equity, pick the first option, submit, see a verdict, press `N`, see a new puzzle. It uses the real generator (a few seconds).
- **Dev proxy:** Vite `server.proxy` sends `/api` to `http://127.0.0.1:8000`. `npm run dev` documents that `uv run serve` must run in `backend/`.

## Review Focus

1. **Contract:** no hand-written response types; `schema.d.ts` and `openapi.json` are fresh (tests in Task 1).
2. **Only legal answers:** the answer panel offers exactly the stored options plus custom sizes only when allowed, sends exactly one of `option` / `custom_to`, never sends `range_read_guess` on the river, and sends `intent` only with a bet or raise. Tests in Task 4.
3. **bb formatting:** odd chip counts show `.5`; no float noise (`0.30000000000000004`); custom bb ↔ chips round-trips. Tests in Task 1 (`format`) and Task 4.
4. **Shortcuts:** never fire while typing; `Enter` can't double-submit; every listed key works and is hinted. Tests in Task 4 and Task 5.
5. **Flow:** resume after reload, skip, next, 404/409/422/503 handling, no request storm (one request per user action; React StrictMode double effects are guarded). Tests in Task 5.
6. **Hidden until submit:** Villain cards face down, undealt board absent before the submit response. Tests in Task 5.
7. **Visual quality:** screenshots of the gallery and the live app at 1280×800 and 1920×1080, plus 1024 wide, are reviewed for alignment, contrast (WCAG AA for text), and the polish bar in spec §11. Reduced motion verified.
8. **Cross-platform:** scripts are Node or npm only; CI green on Windows and macOS.

## Process notes (for the controller)

- Implementer agents do not commit, push, or edit files outside their task's list. The controller stages only the task's paths (never `git add -A`) and commits under the repository's configured identity with the roadmap message, with no co-author or tool trailers, and no mention of any AI tool in code, comments, commits or docs.
- Every task's reviewer gets: this plan, the task's diff, the test output and (for UI tasks) the screenshots. The reviewer checks spec compliance first, then code quality, and does a mutation check on the most important tests (break the code, see the test fail, restore). Findings are fixed by the implementer (or a fresh agent) before the commit.
- Tasks 2 and 4 run in parallel after Task 1; Task 3 after Task 2; Task 5 after Tasks 3 and 4. Commits stay in roadmap order.
